Milvus 是一款开源向量数据库，常用于 RAG 知识库、智能问答、推荐系统和语义检索场景。它可以存储高维向量，并通过近似最近邻搜索快速找到与用户问题语义相近的文档片段。

在 EduRAG 系统中，文档通常会先经过读取、清洗、切分、向量化、入库等步骤。离线阶段负责构建知识库，在线阶段负责根据用户问题进行检索、重排序和 Prompt 拼接。

文档切分通常分为父块和子块。子块粒度较小，适合用于精准召回；父块内容更完整，适合在生成回答时提供上下文。一个常见策略是：检索时命中子块，拼接 Prompt 时使用对应父块，从而兼顾召回精度和上下文完整性。

BGE-M3 是一种适合 RAG 场景的嵌入模型。它既可以生成稠密向量 dense vector，也可以生成稀疏向量 sparse vector。稠密向量更擅长捕捉语义相似度，即使用户问题和原文用词不同，也可能召回相关内容。稀疏向量更擅长捕捉关键词匹配、术语匹配、编号匹配和专有名词匹配。

稠密检索适合处理语义表达不同但含义接近的问题。例如，用户问“如何让问答系统找到相关资料”，稠密检索可能召回“RAG 系统通过向量检索从知识库中召回相关文档”。虽然两句话的字面词语不同，但语义接近。

稀疏检索适合处理关键词非常重要的问题。例如，用户问“SPARSE_INVERTED_INDEX 的作用是什么”，稀疏检索可以直接利用 SPARSE_INVERTED_INDEX 这个精确术语召回相关内容。如果只使用稠密检索，模型可能理解大意，但对具体字段名、模型名、参数名的命中不一定稳定。

混合检索会同时使用稠密向量和稀疏向量。系统可以先分别对 dense_vector 和 sparse_vector 执行检索，再用加权融合策略合并结果。例如可以使用 dense 权重 0.7、sparse 权重 0.3。这样既能保留语义召回能力，也能增强关键词和专业术语命中能力。

在 Milvus 中，稠密向量字段通常可以定义为 FLOAT_VECTOR，例如字段名 dense_vector，维度与嵌入模型输出一致。BGE-M3 的稠密向量维度通常为 1024。稀疏向量字段可以定义为 SPARSE_FLOAT_VECTOR，例如字段名 sparse_vector。稀疏向量通常表示为 token_id 到权重的映射。

构建 Milvus Schema 时，除了向量字段，还应保存文本和元数据。例如 id、text、parent_id、parent_content、source、child_index、embedding_model、created_at 等字段。text 用于保存子块文本，parent_content 用于保存父块完整上下文，parent_id 用于将子块映射回父块，child_index 用于记录子块在父块中的顺序。

dense_vector 可以使用 IVF_FLAT 索引，并采用 IP 作为相似度度量。由于 BGE-M3 输出向量通常会进行归一化，IP 可以近似表示余弦相似度。sparse_vector 可以使用 SPARSE_INVERTED_INDEX 索引，并同样使用 IP 作为匹配分数。

混合检索的一个典型流程是：先使用 BGE-M3 将用户问题编码为 dense query vector 和 sparse query vector；然后分别构造 dense_vector 和 sparse_vector 的检索请求；接着使用 WeightedRanker 对两个检索结果进行融合；最后返回 top_k 个候选子块。

RAG 系统中的重排序器用于对初步召回的候选文档进行精排。初步检索通常更关注召回率，可能会返回一些相关性一般的文档。Reranker 会直接判断 query 与候选文本之间的相关程度，并给出更精确的排序分数。

bge-reranker-large 是常用的中文和多语言重排序模型。它的输入通常是一组 query-document pair，例如 [用户问题, 候选文本]。模型会输出相关性分数，系统可以按照 rerank_score 从高到低选出 top_n 个文档。

相比简单的关键词重叠算法，BGE Reranker 更适合真实 RAG 场景。关键词算法依赖分词结果，容易受到同义表达、短文本、专业术语和分词误差影响。Reranker 能从语义层面判断问题和文档是否真正相关，因此更适合放在混合检索之后做精排。

Prompt 拼接阶段不应该直接拼接所有召回的子块。更合理的做法是根据 reranker 选出的子块找到对应 parent_content，并按 parent_id 去重后拼接为上下文。这样可以避免重复内容，同时保证回答时有足够完整的信息。

当检索结果不理想时，可以从多个方向优化。第一，可以调整分块大小，例如增大 parent_size 提供更完整上下文，或减小 child_size 提升精准召回能力。第二，可以调整 top_k，让检索阶段召回更多候选。第三，可以调整 dense 和 sparse 的融合权重。第四，可以使用更强的 reranker 模型进行精排。第五，可以优化 Prompt，让模型严格基于上下文回答。

如果用户的问题包含大量专业术语、字段名、模型名、函数名或参数名，稀疏检索通常会发挥更明显的作用。例如 BGEM3FlagModel、SPARSE_FLOAT_VECTOR、WeightedRanker、AnnSearchRequest、drop_ratio_search 这类词，很适合通过稀疏向量提高命中率。

如果用户的问题表达比较口语化，或者没有使用文档中的原始关键词，稠密检索通常会更有帮助。例如用户问“为什么要先找小片段再给大段内容”，稠密检索可以匹配到“子块用于精准召回，父块用于提供完整上下文”。

一个优秀的 RAG 系统通常不会只依赖单一检索策略。稠密检索解决语义相似问题，稀疏检索解决关键词精确匹配问题，reranker 解决候选结果精排问题，Prompt 约束解决回答可靠性问题。多阶段组合可以显著提升最终问答效果。
